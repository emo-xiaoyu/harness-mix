# Harness 跨会话任务接力设计

> 实施状态（2026-09-13）：P0–P4 已在当前工作区落地，包括持久化检查点、脱敏证据、四种图形化模式、受当前任务约束的只读 MCP 查询，以及 `checkpoint-created → verifying → active/failed` 状态。P5 已完成脚本级链路与真实 Electron 组件渲染，尚未重启用户正在运行的 Codex Desktop 做 A → B → A 人工验收。

## 1. 背景

Harness Mix 支持在同一个 Codex Desktop 原生任务窗口中使用不同的 Coding Harness。典型场景包括：

- Harness A 完成问题分析，由 Harness B 继续编码。
- Harness A 给出解决方案，由 Harness B 执行方案。
- Harness A 完成修改，由 Harness B 独立审查。
- 当前 Harness 暂停、不可用或额度不足，切换其他 Harness 继续任务。
- 完成阶段性工作后切回原 Harness 复核。

任务接力的目标不是简单切换模型，也不是创建一个互不相关的新会话，而是在保留任务窗口、对话记录和文件现场的前提下，更换继续执行任务的原生 Harness。

## 2. 设计目标

任务接力需要满足以下目标：

1. 保留同一个 Harness Mix 任务窗口、标题和可见对话历史。
2. 保留工作目录、文件变更、Git 状态和 Review 记录。
3. 让目标 Harness 获得足够的任务语义和验证证据。
4. 支持以后切回原 Harness，并恢复其原生会话。
5. 不复制或代理账号凭据。
6. 不迁移审批决定、待审批状态或私有工具状态。
7. 不把不同 Harness 的工具调用协议强行互相转换。
8. 所有交互继续在 Codex Desktop 原生界面中呈现，不增加第二套任务 UI。

## 3. 当前实现

当前实现采用“Host 线程保留 + 一次性上下文信封”的方式。

### 3.1 切换过程

切换时：

1. 确认当前任务没有正在执行的回合、待结算的文件变更或正在建立的 Harness 连接。
2. 关闭当前 Harness 的原生进程。
3. 将当前 Harness 的原生 Session ID、会话文件、模型和选项写入 `harnessChain`。
4. 将任务的当前执行者切换为目标 Harness。
5. 如果目标 Harness 以前执行过该任务，恢复它原来的原生 Session；否则创建新的原生 Session。
6. 创建 `pendingHandoff`，等待用户发送下一条真实消息。
7. 下一条消息发送时注入隐藏的 `[Harness Mix handoff]` 上下文信封。
8. 信封成功发送后清除 `pendingHandoff`。

`/switch <Harness 名> [备注]` 仍可作为键盘入口；图形入口位于任务输入框旁的 Harness 选择器中。

### 3.2 当前交接内容

当前上下文信封包含：

- 任务标题和工作目录。
- 消息总数。
- 最近最多 10 条用户或助手消息，并保持真实先后顺序。
- 总文本预算最多 24,000 字符。
- 普通消息最多保留 4,000 字符。
- 最新一条助手方案最多保留 12,000 字符。
- 最近计划。
- 最多 20 个变更文件。
- 用户填写的交接说明。

目标 Harness 被明确要求使用自己的工具检查真实文件状态，再继续修改。

### 3.3 当前不会传递的内容

当前实现不会向目标 Harness 传递：

- 原始工具调用栈。
- Tool Call ID、Interaction ID 或审批 ID。
- Shell 和其他工具的完整原始输出。
- 待审批、待回答或尚未完成的交互状态。
- 原 Harness 的私有内存和私有协议状态。
- 凭据、令牌、账号密钥或敏感环境变量。

如果测试结果或错误信息已经写入原 Harness 的最终回答，它会作为助手消息的一部分进入交接上下文；如果信息只存在于工具卡片中，则当前不会完整传递。

## 4. 当前方案的局限

一次性 Prompt 信封实现简单，但存在以下限制：

- 对话较长时必须截断，无法保证所有历史都进入目标上下文。
- 工具结果主要依赖原 Harness 是否在最终回答中主动总结。
- 大量上下文一次性注入会占用目标 Harness 的上下文窗口。
- 目标 Harness 无法按需获取某条历史、某个测试结果或某个文件证据。
- 信封发送后即清除，缺少可重复查询和审计的交接对象。
- 仅靠自然语言摘要难以稳定表达计划状态、错误来源和验证结果。

## 5. 推荐方案：持久化接力检查点

推荐将任务接力升级为：

> Host 持久化的 Handoff Checkpoint + 紧凑首轮摘要 + 按需读取上下文和证据。

切换时不再只生成临时 Prompt，而是创建一份不可变、可审计的接力检查点。目标 Harness 首轮收到紧凑摘要，并可按需读取详细信息。

### 5.1 核心流程

```text
源 Harness
  ↓
Host 创建 Handoff Checkpoint
  ├─ 任务目标与约束
  ├─ 决策和计划状态
  ├─ 对话索引
  ├─ 文件与 Diff 证据
  ├─ 测试和错误证据
  └─ 来源与内容哈希
  ↓
切换到目标 Harness
  ↓
目标 Harness 接收紧凑摘要
  ↓
目标 Harness 按需读取历史或证据
  ↓
目标 Harness 核对工作区后继续执行
```

### 5.2 建议的数据结构

```json
{
  "checkpointId": "handoff-...",
  "threadId": "thread-...",
  "sourceHarnessId": "claude-code",
  "targetHarnessId": "pi",
  "createdAt": 1789300000000,
  "intent": "execute-plan",
  "note": "按上一位给出的方案继续执行",
  "task": {
    "title": "修复登录模块",
    "cwd": "E:/project",
    "objective": "...",
    "constraints": ["..."],
    "decisions": ["..."]
  },
  "plan": {
    "completed": ["..."],
    "inProgress": ["..."],
    "pending": ["..."]
  },
  "conversationRefs": [
    { "messageId": "...", "role": "assistant", "digest": "..." }
  ],
  "fileState": {
    "gitHead": "...",
    "diffDigest": "...",
    "changedFiles": ["src/login.js"]
  },
  "evidenceRefs": ["evidence-1", "evidence-2"],
  "unresolved": ["..."],
  "contentDigest": "..."
}
```

该对象应保存在 Host 的独立持久化存储中，不写入用户项目目录，也不要求某个 Harness 自己维护。

## 6. 标准化证据记录

工具调用不应原样迁移，但可以转换为有界、脱敏、只读的证据记录。

```json
{
  "evidenceId": "evidence-1",
  "kind": "test",
  "sourceHarnessId": "claude-code",
  "command": "npm run test:core-all",
  "exitCode": 0,
  "summary": "核心测试全部通过",
  "stdoutExcerpt": "...",
  "stderrExcerpt": "",
  "files": [],
  "createdAt": 1789300000000,
  "contentDigest": "..."
}
```

### 6.1 建议保留的证据

- 测试命令、退出码和结果摘要。
- 构建命令、退出码和关键诊断。
- 有界、脱敏后的 stdout/stderr 片段。
- Git 状态和 Diff 摘要。
- 文件变更路径与内容哈希。
- 未解决错误及其来源。
- 只读检查结果。

### 6.2 明确禁止迁移的内容

- 凭据、令牌和敏感环境变量。
- 原生审批结果或待审批状态。
- 可重放的 Tool Call ID 和 Interaction ID。
- 未完成操作的自动重试指令。
- 原 Harness 专用的内部对象或协议帧。
- 未经脱敏的完整环境信息。

证据内容需要经过统一脱敏和大小限制，并标记为来自历史会话的不可信数据。

## 7. 按需上下文读取

目标 Harness 不需要一次性接收全部历史。Host 可以提供只读查询能力：

- `handoff/get`：读取检查点摘要。
- `handoff/conversation/list`：分页读取相关对话。
- `handoff/evidence/list`：列出测试、错误和构建证据。
- `handoff/evidence/read`：读取指定证据。
- `handoff/files/list`：读取文件变化和 Diff 摘要。
- `handoff/plan/read`：读取结构化计划状态。

具体传输方式应按 Harness 的真实能力选择：

- 支持原生 MCP 的 Harness：提供只读、当前任务授权的本地 MCP 工具。
- 支持其他原生扩展协议的 Harness：通过对应 Adapter 映射只读读取能力。
- 不支持按需工具的 Harness：退化为有界的一次性上下文信封，并明确声明限制。

不能假定所有 Harness 都支持同一种工具协议。

## 8. 图形交互设计

### 8.1 入口

已由 Harness Mix 管理的任务，在输入框旁当前 Harness 图标上显示接力角标。点击后，选择其他可用 Harness。

### 8.2 接力确认弹窗

弹窗建议包含：

- 当前 Harness → 目标 Harness。
- 接力模式。
- 可选交接说明。
- 将要交接的内容预览。
- 当前回合运行状态。
- 取消和确认接力按钮。

### 8.3 接力模式

建议提供四种模式：

| 模式 | 行为 |
| --- | --- |
| 继续执行 | 沿用当前目标、计划和未完成步骤 |
| 执行上一方案 | 优先携带最新方案、待办和验证要求 |
| 独立审查 | 保留证据，但要求目标 Harness 重新检查结论 |
| 重新分析 | 重点携带目标和文件现场，弱化上一 Harness 的结论 |

### 8.4 内容预览

用户可查看或选择是否包含：

- 最新方案。
- 近期对话。
- 当前计划。
- 测试和构建证据。
- 文件变更摘要。
- 未解决错误。

凭据、审批和私有工具状态不应出现在可选项中，因为它们始终禁止迁移。

## 9. 目标 Harness 的接管确认

目标 Harness 不应直接相信历史数据。建议在开始编辑前完成接管确认：

1. 读取接力摘要。
2. 检查当前工作目录。
3. 检查 Git 状态和 Diff。
4. 核对关键文件和未完成计划。
5. 报告接管成功，或说明检查点与真实文件状态之间的差异。

Host 可将接力状态表示为：

```text
checkpoint-created → target-opening → verifying → active
                                     ↘ failed
```

接管失败时保留检查点和原 Harness 会话引用，允许用户切回或更换其他 Harness。

## 10. 原生所有权与安全边界

任务接力不能改变 Harness Mix 的原生所有权原则：

- 每个 Harness 继续拥有自己的原生 Session、模型调用和工具执行。
- 每个 Harness 继续使用自己的账号和凭据存储。
- 权限请求由目标 Harness 按自己的协议重新发起。
- Host 不复制审批结果，不自动批准任何请求。
- Host 只保存非敏感任务检查点和脱敏证据。
- 历史文本、证据和摘要统一标记为不可信数据，不能提升为高优先级指令。
- 目标 Harness 必须以真实文件状态为最终依据。

## 11. 官方 Codex 的特殊边界

Codex Desktop 中的“官方原生 Codex”任务由官方 app-server 直接拥有，不经过 Harness Mix HostRuntime。Harness Mix 无法诚实地原地更换这种线程的执行者。

可支持的方式是“一键克隆为 Harness Mix 管理任务”：

1. 读取允许访问的任务上下文。
2. 创建新的 Harness Mix Host 任务。
3. 创建首个 Handoff Checkpoint。
4. 在原生界面中打开新任务。

这种方式可以在交互上接近接力，但底层是新任务，界面必须明确提示，不能伪装成原官方线程。

使用 Harness Mix 管理的 `Codex（协作）` 时，可以参与真正的同任务跨 Harness 接力。

## 12. 当前实现与推荐方案对比

| 当前实现 | 推荐实现 |
| --- | --- |
| 一次性 Prompt 信封 | 持久化 Handoff Checkpoint |
| 固定截取近期文本 | 紧凑摘要加按需分页读取 |
| 传递变更文件清单 | 传递 Diff 摘要、哈希和来源 |
| 工具结果依赖最终回答 | 标准化、脱敏的证据记录 |
| 信封发送后清除 | 检查点可审计、可重复查询 |
| 新 Harness 直接继续 | 先核对工作区并确认接管 |
| 单一接力行为 | 继续、执行方案、审查、重新分析四种模式 |

## 13. 分阶段实施计划

### P0：持久化接力基础

- 定义 `HandoffCheckpoint` 和 `HandoffEvidence` 数据结构。
- 增加独立、串行化的 Host 存储。
- 在切换时生成不可变检查点。
- 保留当前一次性信封作为兼容投影。
- 使用稳定内容哈希支持去重和审计。

### P1：证据归一化

- 从 Core Item 中抽取测试、命令、错误和文件证据。
- 统一脱敏、截断和大小限制。
- 禁止保存凭据、审批状态和可重放工具 ID。
- 增加证据来源与内容哈希。

### P2：图形化模式与预览

- 在接力弹窗中增加四种接力模式。
- 增加“将要交接的内容”预览。
- 展示运行中、检查中、接管成功和失败状态。
- 保持所有 UI 位于现有原生任务界面。

### P3：按需读取能力

- 实现 Host 侧只读 Handoff API。
- 对支持原生 MCP 的 Harness 提供受限读取工具。
- 为其他 Adapter 提供能力映射或明确降级。
- 增加分页、权限校验和当前任务作用域限制。

### P4：接管确认与恢复

- 目标 Harness 首轮执行确定性工作区核对。
- 记录目标接管确认和差异。
- 接管失败时支持重试、切回或更换目标。
- 重启后保留检查点，但不自动重放可能产生副作用的操作。

### P5：真实桌面验收

- Harness A 给出长方案，Harness B 完整接收并执行。
- Harness A 产生测试失败证据，Harness B 按需读取并修复。
- Harness B 修改文件后切回 Harness A 审查。
- 验证运行中阻止接力、不可用 Harness、接管失败和重启恢复。
- 验证凭据、审批与原始工具 ID 从未进入检查点。
- 在真实重启后的 Codex Desktop 中验证选择、弹窗、确认、首轮发送和切回流程。

## 14. 验收标准

推荐方案完成后，应满足：

- 用户不需要输入命令即可完成任务接力。
- 任务窗口、标题、对话和文件现场保持不变。
- 最新长方案不会因普通单轮截断而丢失关键内容。
- 目标 Harness 可以按需读取历史和标准化证据。
- 工具调用协议和审批状态不会跨 Harness 迁移。
- 接力检查点可持久化、查询、校验和审计。
- 不支持按需读取的 Harness 会明确降级，不静默丢失能力。
- 切回旧 Harness 时恢复其原生会话和模型选项。
- 所有凭据、权限和审批继续由各原生 Harness 所有。
- 真实桌面完成 A → B → A 的端到端接力验证。
